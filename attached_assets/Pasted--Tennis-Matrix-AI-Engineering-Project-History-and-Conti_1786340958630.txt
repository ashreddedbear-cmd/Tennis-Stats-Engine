# 1. Executive Summary

### 1.1 Model claims were materially overstated

**Status:** ✅ Completed & Verified  
**Changed / finding:** The original headline claims—approximately 66% win rate, 65.8% Strong-agreement accuracy, and 64.3% for the “High Data Quality + Low Upset Risk” combination—were validation-sample results, not held-out test results. The canonical held-out Strong-agreement benchmark is 57.9% on 3,144 rows.  
**Why:** Segment mixing created false confidence and made retrospective results look deployable.  
**Evidence:** `audit-task116-full-statistical-audit.md` reported 57.9% on 3,144 test rows; `audit-task162-full-prediction-accuracy-audit.md` reported 65.8% on 2,341 validation rows; `audit-task125-trade-combination-performance.md` contained validation-only combo results. Task 116 used a fresh four-fold expanding-window backtest dated 2026-07-14; Task 162 used a live development snapshot dated 2026-07-15 with no test rows available.  
**Verified:** Yes, by repeated read-only reconciliation across independent sessions.  
**Production-ready:** The 57.9% figure is suitable as the reporting baseline, but the model is not established as a real-money edge.  
**Additional testing:** Re-run all headline buckets on a locked, current test segment with sample size, date range, raw wins/losses, confidence intervals, and number of comparisons disclosed.  
**Undo later:** Do not restore the superseded 65.8% or 66% figures as canonical claims.

### 1.2 Tie-break behavior is a verified high-impact weakness

**Status:** 🟡 Completed – Needs Live Verification  
**Changed / finding:** A live test-segment query found 66.8% accuracy when `tieBreakerApplied=false` (`n=36,682`) and 53.5% when `tieBreakerApplied=true` (`n=15,737`). A forward-only “soft no-play” fix was built and passed 82/82 unit tests, but was not yet proven active on a real new production prediction.  
**Why:** Forced selections in ambiguous matches were barely above coin-flip accuracy and materially reduced blended accuracy.  
**Evidence:** Direct live query over `evaluation_predictions.feature_snapshot->engine->tieBreakerApplied`; code scope and 82/82 unit-test result. Overall across false/true/null cohorts was calculated at roughly 62.8% over 52,456 rows, but this is a broad test slice and not comparable to the Strong-agreement-only 57.9%.  
**Verified:** Accuracy gap and unit behavior are verified; live activation and accuracy lift are not.  
**Production-ready:** Mechanically tested, but not outcome-verified.  
**Additional testing:** Inspect a new prediction row after deployment; then run a locked same-row-set A/B or shadow comparison.  
**Undo later:** Roll back if abstention is not correctly surfaced, silently breaks downstream consumers, or fails to improve a prospectively locked evaluation.

### 1.3 Data Quality was inverted and its blend was incomplete

**Status:** 🟡 Completed – Needs Live Verification  
**Changed / finding:** “Excellent” Data Quality historically performed worst at 54.7%, while “Limited” performed best at 61.4%. The DQ blend was changed in `dataQuality.ts` and `index.ts` to restore missing Availability, Fatigue, and Match Load Recovery inputs and address a tournament-level selection effect.  
**Why:** DQ was being presented as a reliability/truth signal despite almost no positive relationship with correctness and an inverted observed ordering.  
**Evidence:** `audit-task111-dq-degradation-above-55.md`; targeted prediction-engine testing reported 198 tests with 197 passing in one run; later consolidated tests reported 93 tests for the DQ area and 102/102 across DQ, fallback instrumentation, and frozen-backtest test groups.  
**Verified:** Code mechanics and root-cause implementation are tested; real predictive improvement is not verified.  
**Production-ready:** The label-correctness fix can operate in production, but should not be described as an accuracy improvement.  
**Additional testing:** Prospective DQ-tier calibration and accuracy on a locked cohort; confirm high-DQ no longer underperforms low-DQ.  
**Undo later:** Possible if restored inputs worsen calibration or the tournament-level correction introduces selection bias.

### 1.4 Fallback observability is live, but fallback accuracy is unknown

**Status:** ✅ Completed & Verified  
**Changed / finding:** Persisted `used_fallback` and `fallback_sources` instrumentation was wired into evaluation/prediction write paths, backed by migration `0002_add_evaluation_prediction_fallback_columns.sql`, applied live, and confirmed by a direct schema query returning both columns. `data_segment` was also part of the broader instrumentation design and code paths, though live-schema history was inconsistent.  
**Why:** `serveReturn.ts`, `recentForm.ts`, and `index.ts` silently substitute neutral/default values when data is missing. Without row-level flags, fallback-affected accuracy could not be separated from clean predictions.  
**Evidence:** Migration ran via `psql`; information-schema verification returned two matching rows; commit was pushed to `origin/main`; write paths showed real values such as `usedFallback: fallback.usedFallback` rather than stubs.  
**Verified:** Columns and wiring verified; cohort accuracy effect not verified.  
**Production-ready:** Yes for telemetry/data collection. It does not itself improve predictions.  
**Additional testing:** Allow new data to accumulate, then compare clean vs fallback-affected accuracy by source, tour, surface, sample size, and confidence.  
**Undo later:** Keep by default; remove only if write-path/schema compatibility causes production failures. Do not remove fallbacks themselves before an abstention design exists.

### 1.5 Frozen-vs-dynamic weighting remains untestable from existing rows

**Status:** ❌ Still Open  
**Changed / finding:** `backtestFrozenVsDynamicWeights.ts` was built and executed. It found 52,419 frozen/evaluation rows, zero dynamic rows, and zero intersected matches. A system-wide query confirmed `optimizer_run_id IS NOT NULL` for zero rows across every segment and `run_kind`; `optimizer_rows=0`, `first_seen=null`, and `last_seen=null`.  
**Why:** Recent Form weighting changes approximately 13× (1.3 versus 0.1) under match-dependent conflict gates, but no evidence shows that this complexity improves accuracy.  
**Evidence:** Script output and two direct SQL queries. `optimizer_run_id` is the intended discriminator for optimizer-generated historical-test rows in this pipeline.  
**Verified:** Absence of dynamic persisted data is verified. Comparative accuracy is not available.  
**Production-ready:** The diagnostic script is usable; the dynamic weighting architecture is not validated.  
**Additional testing:** Trigger a real optimizer/training run through `candidateOptimizer.ts` with `evaluationOnly:false`, persist tagged test rows, and compare identical `historical_match_id` sets.  
**Undo later:** Dynamic weighting is a rollback/simplification candidate if the eventual frozen comparison shows no improvement or worse calibration.

### 1.6 Engineering workflow itself caused false “done” states

**Status:** ✅ Completed & Verified  
**Changed / finding:** Agent sandbox work and the actual Codespace/Shell repository were sometimes disconnected. Multiple files reported as created did not exist in the real checkout.  
**Why:** This caused repeated phantom completions, missing migration/backtest artifacts, and wasted verification cycles.  
**Evidence:** Shell searches found no migration or frozen-backtest script after prior “created” reports; files were later rebuilt in the real checkout. At least three file incidents occurred, including the migration and backtest script more than once.  
**Verified:** Yes.  
**Production-ready:** New workflow rule is production-process ready: verify every artifact via real-shell `git status`, `find`/`rg`, diff, tests, commit, and push.  
**Additional testing:** None for the finding; enforce via CI and handoff checklists.  
**Undo later:** Never return to summary-only acceptance.

# 3. Problems Discovered

### 3.1 Retrospective data mining presented as prediction

**Status:** ❌ Still Open  
**Changed / finding:** “Best” combinations were selected from many historical buckets after outcomes were known. Samples of 209–311 are too thin for confident superiority claims; 64.1% on 209 cases was estimated to have a broad interval around approximately 57–71%.  
**Why:** Multiple comparisons and selection after observing outcomes create overfitting. Parlays compound leg risk and correlation.  
**Evidence:** Original audit critique and validation-only combo reports.  
**Verified:** Methodological issue verified; exact number of attempted combinations remains unknown.  
**Production-ready:** No as an advertised predictive edge.  
**Additional testing:** Pre-register rules, disclose comparisons, and evaluate on fresh held-out/prospective data.  
**Undo later:** Remove “highest winning combination” marketing if it cannot pass held-out validation.

### 3.2 Silent neutral/default fallbacks

**Status:** ❌ Still Open  
**Changed / finding:** Missing data is replaced in `serveReturn.ts`, `recentForm.ts`, and `index.ts` without a user-facing warning or abstention.  
**Why:** Placeholder-driven predictions can look equally supported and contaminate aggregate accuracy.  
**Evidence:** Code inspection; later instrumentation added to measure usage.  
**Verified:** Existence verified; accuracy harm not measured.  
**Production-ready:** Fallback mechanism is operational but risk handling is not.  
**Additional testing:** Source-specific fallback frequency and accuracy; verify whether 50/50 or confidence failures correlate with fallback paths.  
**Undo later:** Do not simply delete fallback code; replace risky fallback outputs with transparent low-confidence/no-play behavior when evidence supports it.

### 3.3 No stake/position-sizing engine

**Status:** ❌ Still Open  
**Changed / finding:** No bankroll, Kelly, or fixed-fraction logic exists. `ResponsibleGambling.ts` supplies advisory text only.  
**Why:** Even calibrated probabilities do not translate into disciplined real-money risk without sizing and odds/edge logic.  
**Evidence:** Repo inspection summarized in the audit.  
**Verified:** Yes.  
**Production-ready:** Predictions may be displayed, but the product should not imply automated risk management.  
**Additional testing:** Only after probability calibration and actual odds integration are validated.  
**Undo later:** No.

### 3.4 No audit-to-real-bet linkage

**Status:** ❌ Still Open  
**Changed / finding:** Engine self-audits are not connected to the user’s selected bets, odds, timing, stakes, cash-outs, or realized P&L.  
**Why:** Prediction correctness and real trading profitability are different datasets and objectives.  
**Evidence:** No trade-log relationship was found.  
**Verified:** Yes.  
**Production-ready:** Internal accuracy cannot be marketed as user profitability.  
**Additional testing:** Build an append-only trade ledger and reconcile signals at decision time.  
**Undo later:** No.
