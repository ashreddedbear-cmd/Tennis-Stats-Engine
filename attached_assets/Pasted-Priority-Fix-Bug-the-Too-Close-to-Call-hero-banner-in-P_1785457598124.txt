Bug: the "Too Close to Call" hero banner in PredictionResult.tsx displays prediction.calibratedProbability, but tieBreakerApplied is set based on rawEnsembleProbability being within TIE_BAND of 50 (see index.ts line ~485-497). These are different values from different pipeline stages, and nothing keeps them consistent — confirmed real cases where the banner reads "too close to call / no strong signal" while the displayed percentages show 100.0%/0.0% (e.g. E. Root cause: calibration, segment-specialist blending, and simulator blending all run AFTER the tie-breaker check, and can push the probability to an extreme even when the raw ensemble was genuinely a coin flip.

Fix needed — pick the correct semantic, don't just patch the display:

2. Whether calibratedProbability swinging to an extreme AFTER a tie-breaker determination should itself invalidate tieBreakerApplied (i.e. re-check tie-band membership on the FINAL calibratedProbability, not just the raw input).

Investigate which of these two matches the intended product behavior, fix accordingly, and add a test that specifically catches this case: rawEnsembleProbability near 50 (triggering tieBreakerApplied) combined with a calibration/specialist/simulator path that pushes calibratedProbability to an extreme — assert the displayed banner and the displayed percentage are never contradictory again.

Also audit whether this same inconsistency exists anywhere else calibratedProbability is displayed without checking tieBreakerApplied's underlying rawEnsembleProbability — report all locations found, don't just fix PredictionResult.tsx in isolation.

Confirmed bug in builderScoringService.ts: risk and validation scoring can improve (lower risk, higher score, Elite tier) at the exact moment a matchup's opponent-side data collapses (e.g. Michael Zheng dropping to "1 match found"). Two root causes, both need fixing:

1. `if (sel.total < 10) risk += 12` only checks the SELECTED player's total match count. Add an equivalent check for the opponent (`opp.total < 10`) so thin opponent data is penalized the same way thin selected-player data is.

2. `if (agreementRate > 0.75) risk -= 8` has no sample-size gate — a 3/3 (100%) unanimous agreement from a collapsed factor set gets the same or stronger risk reduction as a 7/8 (88%) agreement from a full factor set. Add a minimum `available` count (e.g. available >= 5) before this bonus applies, so a small coincidental-agreement sample can't outscore a larger, more genuinely-tested one.

3. Add a consistency check (similar to the prediction engine's checkFinalConsistency) that catches the specific contradiction just reproduced: a card showing "Very limited match history for [player]" or "INSUFFICIENT DATA" should never simultaneously be eligible for ELITE tier or a risk score below some floor (e.g. risk < 20). If both conditions are true, force the tier down and flag it as a caught inconsistency, the same pattern already used in the prediction engine's finalConsistencyCheck.ts.

Write a test reproducing this exact scenario: a matchup where available opinionated factors drop from a large number to a small one (e.g. 8→3) due to one player's data becoming unavailable, all remaining factors happening to agree, and assert that risk does NOT decrease and tier does NOT improve as a result.
