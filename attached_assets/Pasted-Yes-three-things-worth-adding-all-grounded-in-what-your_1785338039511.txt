PHASE 1 — Fix the tie-break cascade (Task #163) In predictionEngine/tieBreakers.ts, called from predictionEngine/index.ts: this mechanism fires whenever a raw prediction lands within 3 points of a coin flip and picks a directional lean instead of reporting genuine uncertainty. It fires on 38% of graded predictions. Non-applied baseline accuracy is 66.7%; predictions decided by this cascade using Serve & Return score only 53.7%, and using Surface Elo score only 46.7% — worse than random — while still displaying a confident-sounding justification. Investigate why each step fails in the close-to-50/50 regime before reordering or replacing steps. At minimum, the system should be able to honestly report a genuine toss-up rather than assert a lean that performs worse than a coin flip. Add a regression guard so this cannot silently regress again. Pass criteria: tie-break-decided accuracy is statistically indistinguishable from, or better than, the 66.7% non-applied baseline.
PHASE 2 — Stop walk-forward testing from wiping evaluation history (Task #135) walkForward.test.ts currently wipes and rebuilds all evaluation history every time it runs, so there’s no stable, accumulating, genuinely held-out test dataset — meaning the same data used to tune the model is also used to grade it, inflating backtest accuracy numbers. Fix this so evaluation runs retain multiple folds and a real held-out test segment. Pass criteria: evaluation_runs retains multiple folds and a genuine test segment after the test suite runs.
PHASE 3 — Real paper-trading schedule and quiet-pipeline alert (Tasks #129 and #130) Live graded paper-trading volume is currently too low (roughly 158 graded rows) for reliable real-world accuracy claims. Put real paper-trading on a proper recurring schedule, and add an alert that fires if the pipeline goes quiet for an unexpected stretch. Pass criteria: graded paper-trade volume grows steadily week over week, with alerting confirmed working via a deliberate test gap.
PHASE 4 — Parlay Builder risk-floor fix, plus the separation safeguard In src/services/parlayBuilder/builderScoringService.ts, the risk score only rewards conventional-favorite signals and never checks how close the two players actually are. Add an independent closeness signal from data already available — win rate gap, surface win rate gap, market-odds distance from even, ranking gap — and use it as a floor, not an offsettable addition, so a genuinely close matchup can never be scored as low-risk. Do not touch anything under predictionEngine/ for this phase.
Also add a build-time and test-time check that fails automatically if any file under the Parlay Builder directory ever imports anything from the Prediction Engine directory or its results/history/calibration/cards tables. This must run before every build and every test run, so the separation between the two systems can’t quietly break later, including during future AI-assisted edits.
